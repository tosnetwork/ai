# Service Actor Rail Work Frames V1

## Status and scope

**Status:** specification of the deployed format. It describes, byte for byte,
the frames and messages that OpenFox at commit `682c8bc3`
(`pkg/servicebridge/frames.go`, `messages.go`, `receiver.go`, `inbox.go`,
`transport.go`, `buyer.go`, `provider.go`, `receipt.go`) uses to move paid
software work between a buyer and a provider on the Service Actor rail
([`SERVICE_ACTOR_TVM_V1.md`](SERVICE_ACTOR_TVM_V1.md),
[`SERVICE_ACTOR_SETTLEMENT_DESIGN.md`](SERVICE_ACTOR_SETTLEMENT_DESIGN.md)).
Nothing here changes that format. An implementation that follows this
document interoperates with OpenFox without a flag day, so any runtime, not
only OpenFox, can send a paid job to a provider and get its result back.
This is the precondition for a buyer adapter that does not embed OpenFox.

The frozen vectors are
[`service-actor-rail-work-frames-v1.json`](../test-vectors/service-actor-rail-work-frames-v1.json),
generated by the OpenFox encoders at `682c8bc3` (section 14). Where OpenFox
behaviour cannot be stated as a clean rule, section 15 lists it as an open
question instead of inventing a rule.

Key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119. "OpenFox
does" marks observed behaviour that this document records but does not
require of other implementations.

## 1. Roles and authority

- The **buyer** has called the Service Actor: a finalized `call` from its
  wallet carries `request_hash` and `expected_terms_hash` and created request
  `request_id` (`ACCEPTED_QUOTE_TVM_V1.md`, "Request commitment").
- The **provider** owns the Capability and operates the actor; its attestor
  signs the SRP2 statement whose `response_hash` is the Receipt's cell hash,
  and its owner wallet submits `respond`.
- Frames carry claims, never authority. The provider admits work only while
  finalized state shows the paid request pending under the quoted terms
  (section 7.1). The buyer accepts a result only when its Receipt hashes to
  the finalized attested `response_hash` (section 7.2). Payment, refund and
  sweep are decided by the actor alone.

## 2. Carriage

### 2.1 Agent Packets

Every frame travels as the `payload` of exactly one signed Agent Packet V1
([`AGENT_PACKET_V1.md`](AGENT_PACKET_V1.md); JSON schema
`tos.service.agent-packet.v1`). The sender is the buyer Agent for task, ack
and result-request frames, and the provider Agent (the Capability owner) for
result frames. The recipient is the counterparty Agent. The Quote's transport
binding is security mode `2` (`ACCEPTED_QUOTE_TVM_V1.md`): its base URL
`agent-packet:agent_<hex>` names the provider Agent.

Packet fields the sender sets:

| Field | Value |
|---|---|
| `capability_id` | the purchased Capability ID (`cap_<64 hex>`) |
| `quote_commitment` | the Accepted Quote commitment, `tvm-cell-sha256:<64 lowercase hex>` |
| `sequence`, `nonce_hex`, `created_at_unix` | as Agent Packet V1 requires; OpenFox uses a fresh random nonce per packet and a clock-seeded strictly increasing sequence that receivers do not rely on |
| `payload_base64` | one encoded frame (section 3) |

A receiver MUST verify the packet under Agent Packet V1 against finalized
state, MUST require `recipient_agent_id` to be its own Agent, and MUST
refuse a packet whose payload does not start with the frame magic and version
(section 3) before any write; OpenFox refuses it for good. A receiver MUST
bind every message to the packet's verified `sender_agent_id` (section 9).
OpenFox does not compare the packet's `capability_id` or `quote_commitment`
with the frame or the request (section 15, Q1); the request binding is the
frame's.

OpenFox bounds an inbound packet JSON at 131,072 bytes, the Messenger event
bound. One frame (at most 121 + 61,440 bytes) fits a packet within the
Messenger direct-application bound of 96 KiB.

### 2.2 Carriers

A packet reaches the recipient through the Messenger (direct application of
kind `agent.packet`) or through the end-to-end-encrypted Agent Packet Relay
([`AGENT_PACKET_RELAY_V1.md`](AGENT_PACKET_RELAY_V1.md)). Carriers carry the
exact packet JSON and are trusted for nothing. Over the relay carrier the
encryption key cards that let the counterparty seal its replies travel inside
these frames (sections 5.1, 5.2, 5.3, 5.4); `AGENT_PACKET_RELAY_V1.md` section
6.4 gives the rules for taking them.

### 2.3 Packet expiry

Each packet of a message expires at the message's business deadline, never
more than 86,100 seconds (24 hours less 5 minutes) after signing, and an ack
never more than 3,600 seconds after signing:

| Message | Expiry cap |
|---|---|
| task | the request's `response_deadline` |
| result | the result's retention end (section 11.3) |
| result-request | the result's retention end |
| ack | 3,600 s after signing |

A sender MUST NOT sign or send a packet whose deadline has already passed.

## 3. Frame

### 3.1 Layout

All integers are unsigned big-endian. A frame is a 121-byte header followed
by its data.

| Offset | Size | Field | Rule |
|---:|---:|---|---|
| 0 | 4 | magic | `0x4f465231` (ASCII `OFR1`) |
| 4 | 2 | version | `1` |
| 6 | 1 | kind | `1` task, `2` result, `3` ack, `4` result-request |
| 7 | 32 | actor_account | the 32-byte account ID of the workchain-0 actor; non-zero |
| 39 | 8 | request_id | the actor's request ID |
| 47 | 32 | request_hash | the `call`'s `request_hash`; non-zero |
| 79 | 32 | message_digest | SHA-256 of the complete message (section 4); non-zero |
| 111 | 4 | total_length | message length in bytes; 1 to the kind's bound (section 10) |
| 115 | 1 | index | chunk index, below `count` |
| 116 | 1 | count | `ceil(total_length / 61440)`; 1 to 32 |
| 117 | 4 | data_length | exactly the number of bytes that follow |
| 121 | data_length | data | this chunk of the message |

`(actor_account, request_id, request_hash)` is the **request binding** of a
frame. A decoder MUST refuse a frame shorter than 121 bytes or longer than
121 + 61,440 bytes, a wrong magic or version, an unknown kind, any zero
binding field or digest, a `total_length` of 0 or above the kind's bound, a
`count` of 0 or above 32, an `index` at or above `count`, and a `data_length`
that differs from the bytes that follow.

### 3.2 Canonical chunking

A message has exactly one chunking: chunk `i` carries bytes
`[61440 * i, min(61440 * (i + 1), total_length))`. Every chunk but the last
carries exactly 61,440 bytes and the last carries
`total_length - 61440 * (count - 1)` bytes. A decoder MUST refuse a frame
whose `count` is not `ceil(total_length / 61440)` or whose data length is not
the one this rule gives its index.

### 3.3 Joining

A frame set joins when every frame has the same kind, request binding,
`message_digest`, `total_length` and `count`, each index below `count` appears
exactly once, and the concatenated data in index order is `total_length`
bytes whose SHA-256 is `message_digest`. Frames may arrive in any order. A
receiver MUST refuse to join any other set, and MUST refuse a second frame
for an index it holds whose bytes differ from the first. OpenFox discards a
complete set whose digest does not match and waits for a fresh delivery.

## 4. Message container

Every message is

```text
message = header_length:uint32 header:header_length bytes body
```

- `header_length` is 1 to 65,536 and at most the bytes after it.
- `header` is the canonical JSON object of the message kind (sections 4.1 and
  5). Decoding refuses unknown fields, a second JSON value after the object,
  and any header whose bytes differ from the canonical encoding of the decoded
  value.
- `body` is the rest of the message: the source archive of a task, the
  artifact of a result, and empty for an ack and a result-request.

The message's kind is the frame kind; its `message_digest` is SHA-256 over
the whole message including `header_length`.

### 4.1 Canonical JSON

The canonical header is the output of Go `encoding/json` `Marshal` for the
header struct, which is:

- the fields in the order of the tables of section 5, each exactly once, with
  no whitespace;
- integers in plain decimal without sign, exponent, fraction or leading zero;
- strings in double quotes, escaping `"` as `\"`, `\` as `\\`, and `<`, `>`,
  `&` as `<`, `>`, `&`;
- an optional field omitted when its value is empty, never present as `""`.

Every string field except `capability_version` is restricted to characters
that need none of these escapes (patterns of section 5). For
`capability_version` the canonical form of control characters, non-ASCII text
and invalid UTF-8 follows Go's encoder; section 15, Q2.

## 5. Messages

Patterns: `hex64` is `^[0-9a-f]{64}$`; `agent` is `^agent_[0-9a-f]{64}$`;
`cap` is `^cap_[0-9a-f]{64}$`; `wallet` is `^0:[0-9a-f]{64}$`; `sha256` is
`^sha256:[0-9a-f]{64}$`; `b64` is strict standard Base64 with padding (no
non-zero pad bits, no line breaks).

### 5.1 Task (kind 1, schema `tos.openfox.rail-task.v1`)

Sent by the buyer once its `call` is finalized.

| # | Field | Type | Rule |
|---:|---|---|---|
| 1 | `schema` | string | exactly `tos.openfox.rail-task.v1` |
| 2 | `buyer_agent_id` | string | `agent`; the Agent the result returns to |
| 3 | `buyer_wallet` | string | `wallet`; the wallet that sent the `call` |
| 4 | `capability_id` | string | `cap` |
| 5 | `capability_version` | string | 1 to 128 bytes; the Quote's version |
| 6 | `package_base64` | string | `b64` of non-empty bytes: the serialized `QuoteProposalPackageV1` the buyer accepted |
| 7 | `execution_id` | string | `hex64`; section 6.2 |
| 8 | `execution_nonce` | string | `hex64`; opens `execution_id` (section 6.2) |
| 9 | `source_digest` | string | `sha256` of the body |
| 10 | `request_id` | integer | 0 to 2^64-1; the actor's request ID |
| 11 | `call_lt` | integer | 1 to 2^64-1; logical time of the finalized `call` |
| 12 | `call_hash` | string | `hex64`; hash of the finalized `call` transaction |
| 13 | `buyer_key_card_base64` | string, optional | `b64` of the buyer's encryption key card packet JSON; at most 21,848 characters (16,384 bytes decoded) |

Body: the source archive, 1 to 1,048,576 bytes, whose SHA-256 is
`source_digest`. A decoder MUST also refuse a `package_base64` that is not
strict Base64 or decodes to nothing.

### 5.2 Result (kind 2, schema `tos.openfox.rail-result.v1`)

Sent by the provider once its `respond` is finalized.

| # | Field | Type | Rule |
|---:|---|---|---|
| 1 | `schema` | string | exactly `tos.openfox.rail-result.v1` |
| 2 | `response_hash` | string | `hex64`; the attested response hash |
| 3 | `receipt_boc_base64` | string | `b64` of the non-empty Receipt BOC |
| 4 | `provider_key_card_base64` | string, optional | `b64` of the provider's encryption key card packet JSON; at most 21,848 characters |

Body: the artifact, 1 to 1,114,112 bytes.

### 5.3 Ack (kind 3, schema `tos.openfox.rail-result-ack.v1`)

Sent by the buyer once it has accepted a result (section 7.2).

| # | Field | Type | Rule |
|---:|---|---|---|
| 1 | `schema` | string | exactly `tos.openfox.rail-result-ack.v1` |
| 2 | `response_hash` | string | `hex64`; the accepted result's response hash |
| 3 | `buyer_key_card_base64` | string, optional | as in 5.1 |

Body: empty.

### 5.4 Result request (kind 4, schema `tos.openfox.rail-result-request.v1`)

Sent by the buyer when the respond is finalized and it holds no accepted
result. It never admits, executes or responds; the request it names is the
frame's request binding.

| # | Field | Type | Rule |
|---:|---|---|---|
| 1 | `schema` | string | exactly `tos.openfox.rail-result-request.v1` |
| 2 | `buyer_key_card_base64` | string, optional | as in 5.1 |

Body: empty.

## 6. Derived values

### 6.1 Input digest

```text
input_digest = SHA-256("tos.openfox.rail-input.v1" || 0x00 || source_digest_bytes)
```

`source_digest_bytes` is the raw 32-byte SHA-256 of the source archive. The
domain separates the request's input commitment from the bare source digest.

### 6.2 Execution ID

```text
execution_id = SHA-256("tos.openfox.rail-execution-id.v1" || 0x00 ||
                       buyer_agent_id || 0x00 || execution_nonce_bytes)
```

`buyer_agent_id` is its ASCII text and `execution_nonce_bytes` the 32 raw
bytes of `execution_nonce`. The buyer draws a fresh non-zero random nonce per
purchase. Because the paid `call` commits to `execution_id`, a task naming
another return Agent than the one committed cannot open it: nobody who learns
the source can resend the paid task as their own Agent, take the result and
consume the provider's single execution.

### 6.3 Request hash

```text
quote_commitment = cell_hash(accepted_quote)
request_hash     = cell_hash(NSR1(quote_commitment, execution_id, input_digest))
```

as `ACCEPTED_QUOTE_TVM_V1.md` "Request commitment" defines. The Accepted Quote
is the one `package_base64` carries. The vector's `binding` object fixes one
instance.

## 7. Binding to the Service Actor request

### 7.1 Provider admission of a task

A provider MUST, before it executes anything, establish every item below. Any
failure refuses the task without executing (section 12).

1. The message's sender Agent equals `buyer_agent_id`, and the frame's
   `request_id` equals the header's.
2. `package_base64` decodes to a `QuoteProposalPackageV1` that portable
   Quote validation accepts for `capability_id`, `capability_version` and
   `buyer_wallet` on the provider's network; the Quote names this provider,
   Capability and version.
3. The Quote's transport binding is mode `2` naming this provider Agent, and
   the archive is within both its `max_request_bytes` and 1,048,576 bytes.
4. `execution_id` equals 6.2 over `buyer_agent_id` and `execution_nonce`.
5. From one quorum-finalized checkpoint: exactly one successful `call` from
   `buyer_wallet` to the quoted actor carries the `request_hash` of 6.3, and
   it is the `(call_lt, call_hash)` transaction with `expected_terms_hash`
   equal to the Quote's `terms_hash`; existing-request verification
   (`SERVICE_ACTOR_SETTLEMENT_DESIGN.md` section 2.4) accepts it; the call
   created `request_id`; the request is pending; and the provider's own
   execution and respond budgets still end strictly before
   `response_deadline` at the checkpoint's chain time (OpenFox also requires
   the manifest's wall-clock limit to fit its execution budget).
6. The frame's `request_hash` and `actor_account` equal the verified request
   hash and actor (section 15, Q3 on ordering).
7. No other admission of the slot `(quote_commitment, actor, request_id)`
   exists: a slot is executed at most once.

The provider builds the Receipt binding (`SOFTWARE_WORK_RECEIPT_TVM_V1.md`)
from the verified values: `quote_commitment`, `execution_id`, `input_digest`,
`source_digest`, the snapshotted price, its own Agent, the manifest's
toolchain digest and the manifest digest as sandbox digest. It responds only
when the execution succeeded, the Receipt describes the actual outcome, and a
fresh check like item 5 still passes before `response_deadline`.

### 7.2 Buyer acceptance of a result

A buyer MUST accept a result only from the purchase's provider Agent, for the
purchase's frame binding, and only after its respond is finalized:

1. The Receipt BOC is a canonical single-root `SoftwareWorkReceiptV1` (OpenFox
   bounds it at 4,096 bytes) whose cell hash equals the finalized respond's
   `response_hash` and the header's `response_hash`.
2. The Receipt binds the buyer's own `quote_commitment`, `execution_id`,
   `input_digest`, `source_digest`, the request price, the Quote's provider,
   and the manifest's toolchain and manifest digests; `exit_code` is 0 and
   `completed_at` non-zero.
3. SHA-256 of the artifact is the Receipt's `artifact_digest`; the artifact is
   a tar of exactly two regular files, `output.log` and `report.json`, each
   once, whose SHA-256 values are the Receipt's `result_digest` and
   `report_digest`.

A buyer MAY store a result that arrives before the respond is finalized and
validate it later; OpenFox does. OpenFox keeps the first result message it
stores for a purchase and ends the purchase as `receipt-mismatch` when that
message fails these checks (section 15, Q9).

## 8. Integrity summary

| Value | Bound by |
|---|---|
| source archive | `source_digest` (5.1), checked at decode |
| `input_digest` | 6.1 over `source_digest`; in `request_hash` and the Receipt |
| `execution_id` | 6.2; in `request_hash` and the Receipt |
| whole message | `message_digest` of every frame (3.3) |
| Receipt | its cell hash is the finalized `response_hash` (7.2) |
| artifact, output, report | the Receipt's `artifact_digest`, `result_digest`, `report_digest` (7.2) |
| frames of one request | request binding, checked against finalized state (7.1 item 6, 7.2) |
| sender | Agent Packet signature under finalized Agent policy (2.1) |

## 9. Replay and idempotency

- **Message identity.** A receiver identifies a message by
  `(sender_agent_id, kind, actor_account, request_id, request_hash,
  message_digest)`. Frames with the same identity assemble into one message.
  A sender's fresh delivery of the same bytes has the same identity and is a
  duplicate.
- **Duplicates.** A duplicate of a processed message is handled again with
  the same effect: a task again finds its slot taken and executes nothing; a
  result for an accepted purchase is acknowledged again; an ack or a
  result-request changes nothing it already changed. The Agent Packet replay
  guard of `AGENT_PACKET_V1.md` is per packet nonce; OpenFox relies on the
  durable inbox for message-level deduplication instead.
- **Durability before acknowledgement.** A receiver MUST store a frame
  durably before acknowledging its packet to the carrier, so a crash never
  loses a packet the carrier dropped.
- **At most one execution.** The provider's slot `(quote_commitment, actor,
  request_id)` admits once (7.1 item 7). The buyer never reuses a
  `request_hash` (`ACCEPTED_QUOTE_TVM_V1.md`).
- **Redelivery.** A redelivery is a new set of packets (new nonces) carrying
  the same message bytes, or for a result new bytes when the carried key card
  changes; receivers MUST NOT treat a new packet nonce as a new message.
- **Inbox bounds.** OpenFox bounds open (incomplete) assemblies at 8 per
  sender and 64 in total; these are local limits, not protocol limits.

| Quantity | Bound (bytes) |

| frame data | 1 to 61,440 |
| frames per message | 1 to 32 |

## 11. State machine

### 11.1 Buyer

| State | Event | Action |
|---|---|---|
| called | `call` finalized, request pending | send task; go to task-sent |
| task-sent | pending and 600 s since the last task | send the task again (fresh packets) |
| any open | respond finalized, no stored result | send a result-request at once, then at most every 21,600 s until retention end (OpenFox: only when it receives over the relay carrier) |
| any open | respond finalized, result stored | validate (7.2); on success send ack, go to completed |
| completed | result arrives again | send ack again |
| any open | request overdue | send `expire`; then `claim_refund` from the wallet before `refund_claim_deadline` |
| any | request refunded, swept or lapsed | terminal; no frames |

The buyer's refund duty does not depend on any frame: a provider that never
answers is settled by `expire` and `claim_refund`.

### 11.2 Provider

| State | Event | Action |
|---|---|---|
| — | task admitted (7.1) | execute once |
| executed | execution failed or not attestable | no respond; the buyer is refunded by timeout |
| executed | fresh check passes before `response_deadline` | send `respond` |
| responding | respond not finalized, window open | send the same `respond` again (OpenFox: after 60 s) |
| responding | respond finalized | deliver result; go to delivering |
| delivering | unacknowledged | deliver again after 60 s, doubling to at most 3,600 s |
| delivering | result-request from the buyer | take its card; deliver at once, at most once per 600 s |
| delivering | ack from the buyer naming the response hash | go to acked; stop delivering |
| delivering | retention end reached | stop delivering |
| any | task for a taken slot | take its card; never execute again |

### 11.3 Retention

The result's retention end is `response_deadline + retention_seconds`, where
`retention_seconds` is manifest key 19. It runs from the end of the response
window, so a late respond still leaves the full interval for delivery.

### 11.4 Lost messages

- **Lost task:** the buyer resends every 600 s while the request is pending;
  the provider executes at most once.
- **Lost result:** the provider redelivers with backoff until acked or
  retention end; the buyer also asks with a result-request.
- **Lost ack:** the provider redelivers the result; the buyer acks again.
- **Lost result-request:** the buyer asks again after its interval.

## 12. Refusals

No frame carries a refusal or an error code. A refusal is local: the receiver
drops the frame or message and keeps no state for it, and the counterparty
learns the outcome from finalized actor state (a pending request that is
never answered ends in `expire` and `claim_refund`). The names below are
stable labels for implementations and tests, not wire values.

| Label | Condition | Where |
|---|---|---|
| `packet-invalid` | Agent Packet decode or verification fails, or another recipient | 2.1 |
| `not-a-rail-frame` | payload lacks the frame magic and version | 2.1 |
| `frame-invalid` | any rule of 3.1 or 3.2 | 3 |
| `frame-conflict` | a frame differs from the stored frame of its index | 3.3 |
| `join-invalid` | a set that does not join under 3.3 | 3.3 |
| `inbox-full` | local assembly bounds (9) | 9 |
| `message-invalid` | any rule of 4 or 5 | 4, 5 |
| `task-not-admitted` | any item of 7.1 | 7.1 |
| `admission-paused` | the provider's owner paused admission; the task is held, not refused (OpenFox) | 7.1 |
| `slot-taken` | a second task for an admitted slot; not executed, its card is taken | 7.1 item 7 |
| `result-not-accepted` | any item of 7.2 | 7.2 |
| `result-request-refused` | not from the request's buyer, no response to deliver, or retention ended | 11.2 |
| `ack-unmatched` | not from the request's buyer, or another response hash | 11.2 |

OpenFox's packet socket answers `422` for every refusal and `202` once the
frame is durable; a carrier keeps a packet it could not hand over.

## 13. Schema identifiers

The identifiers keep their `tos.openfox.*` names:
`tos.openfox.rail-task.v1`, `tos.openfox.rail-result.v1`,
`tos.openfox.rail-result-ack.v1`, `tos.openfox.rail-result-request.v1`, the
input domain `tos.openfox.rail-input.v1` and the execution-ID domain
`tos.openfox.rail-execution-id.v1`. They are protocol identifiers of this
format, not a statement that only OpenFox may use it. They are not renamed
because:

- the input domain and the execution-ID domain are hashed into
  `input_digest` and `execution_id`, which are committed on chain through
  `request_hash` and the Receipt; renaming them changes every request hash
  and cannot be done by accepting two names;
- the header schemas sit inside canonical headers whose decoders refuse
  every other value; a rename needs every deployed receiver to accept both
  names first, then every sender to switch, which is a coordinated two-release
  migration with no functional gain.

A later version that renames them MUST be a new frame `version` and MUST
specify the dual-acceptance period.

## 14. Vectors and reproduction

[`service-actor-rail-work-frames-v1.json`](../test-vectors/service-actor-rail-work-frames-v1.json)
holds, generated by the OpenFox encoders at `682c8bc3` and checked against its
decoders:

- `binding`: one instance of 6.1, 6.2 and 6.3, with the `NSR1` request hash;
- `receipt`: a canonical Receipt, its response hash, and an artifact whose
  digests it binds;
- `messages`: a two-frame task (its archive given by a rule, its frames by
  header and data range), a one-frame task with a buyer card, results with and
  without a provider card, acks and result-requests with and without a buyer
  card, each with its exact message bytes or digest and every frame;
- `negative_frames`: 18 frames each breaking one rule of section 3, given as
  edits (overwrite, then truncate, then append) of a positive frame and the
  SHA-256 of the result;
- `negative_messages`: 24 messages each breaking one rule of section 4 or 5;
- `negative_joins`: 4 frame sets that must not join.

Key card and package bytes in the vectors are opaque stand-ins: this format
carries them without interpreting them. A stdlib-only reproducer that shares
no code with OpenFox rebuilds every derived value, message and frame and
refuses every negative case:

```bash
python3 -I scripts/reproduce-service-actor-rail-work-frames-v1.py
```

It does not recompute the Receipt cell hash, which the protocol `nativecore`
Receipt codec covers.

## 15. Open questions

- **Q1. Packet fields are not bound.** OpenFox sets the packet's
  `capability_id` and `quote_commitment` (2.1) but no receiver compares them
  with the task's Capability, the verified Quote or a stored purchase. A
  conforming sender sets them as 2.1 says; whether a receiver MUST refuse a
  mismatch is open.
- **Q2. `capability_version` charset.** The frame codec accepts any 1 to 128
  bytes; admission later requires the Quote's version. Its canonical form for
  control characters, non-ASCII text and invalid UTF-8 is Go-specific (4.1).
  Restricting it to the Registry's version syntax would make the canonical
  form portable.
- **Q3. Binding check after slot claim.** OpenFox checks the frame's
  `request_hash` and `actor_account` against the verified request (7.1 item 6)
  after the admission gate has taken the slot. A buyer whose own task frames
  carry a wrong binding consumes its slot without execution and is refunded by
  timeout. Whether the check must precede the slot claim is open.
- **Q4. Package size.** `QuoteProposalPackageV1` may be up to 2 MiB
  (`quoteexchange`), but `package_base64` must fit the 65,536-byte task header
  with the other fields and the card, so about 32 KiB is the practical limit
  with a full card. No explicit package bound is stated.
- **Q5. Receipt size.** A result decodes with a Receipt of any size within the
  header bound; only acceptance (7.2) bounds it at 4,096 bytes.
- **Q6. Result-request only over the relay.** OpenFox sends result-requests
  only when it receives over the relay carrier (its purpose is the in-band card
  refresh); a buyer reached over the Messenger relies on redelivery alone.
- **Q7. No refusal frame.** A buyer learns of a refused task only by timeout
  (section 12). A buyer adapter that must report a failure promptly may need a
  signed refusal frame; none is defined.
- **Q8. Actor workchain.** The frame binds the actor by its
  32-byte account ID only; workchain 0 is implied by the rail
  (`SOFTWARE_WORK_MANIFEST_V1.md` key 21), not carried.
- **Q9. First stored result wins.** OpenFox stores the first result message
  from the purchase's provider and never replaces it; if that message fails
  7.2 the purchase ends as `receipt-mismatch`, although the respond is final
  and the price is paid, and a later valid redelivery is not considered. Only
  the authenticated provider can cause this. Whether a buyer must keep
  accepting redeliveries until one passes 7.2 is open.
